# LESSONS.md — Журнал инженерных уроков

**Назначение:** фиксировать уроки процесса разработки Agent-Nutri (не путать с `learning/` — там знания продукта-агента). Каждая ошибка, которая стоила времени, превращается в правило на будущее.

**Как читать:** перед началом любой сессии разработки Claude/Cline обязан прочитать последние 5 записей (снизу вверх). Ссылка на этот файл — в `CLAUDE.md`, секция «Точка входа при любой команде».

**Как писать:** новая запись добавляется в конец файла при закрытии сессии, если в ней была ошибка или выведено новое правило. Формат строго по шаблону ниже. Записи не редактируются задним числом (append-only).

---

    - **Правило на будущее:** <императивная формулировка: "делай X" или "не делай Y">
    - **Как проверить:** <конкретная команда/условие, показывающее, что правило соблюдено>
    - **Связанные файлы:** <пути через запятую>

### L-053-01 — Транзакционность обязательна для нормализации методологических файлов

- **Дата:** 2026-07-30
- **Сессия:** Session 53 (Этап F.2 — EBM-обогащение vitamins.md)
- **Контекст:** первый прогон EBM-скрипта на большом методологическом файле, изменения писались напрямую без промежуточной валидации.
- **Что пошло не так:** при частичном сбое одного из патчей файл оставался в промежуточном состоянии, часть тегов уже вставлена, часть нет. Восстановление вручную заняло больше времени, чем сама сессия.
- **Корневая причина:** отсутствовал шаг Validate между Apply-Patch и Write. Скрипт писал файл, даже если валидация не проходила.
- **Правило на будущее:** каждый normalize-скрипт строится по схеме **Read → Apply-Patch (in-memory) → Validate → Write**. Если валидация падает хоть на одной проверке — файл НЕ записывается, backup остаётся нетронутым, скрипт возвращает ненулевой exit code. В начало скрипта — guard идемпотентности (проверка маркера `EBM_ENRICHED_vX.Y`).
- **Как проверить:** в теле скрипта присутствуют три отдельных блока с явными комментариями `# === APPLY ===`, `# === VALIDATE ===`, `# === WRITE ===`, причём `Set-Content` вызывается только внутри `if ($validationPassed) { ... }`.
- **Связанные файлы:** `scripts/normalize_vitamins_v1.ps1`, `scripts/normalize_nervous_system_v1.ps1`, `scripts/normalize_female_hormones_v1.ps1`.

### L-054-01 — В PowerShell 5.x не использовать multiline here-strings внутри -Command

- **Дата:** 2026-07-31
- **Сессия:** Session 54 (Этап F.2 — EBM-обогащение nervous_system.md)
- **Контекст:** попытка передать скрипт с многострочным блоком `@'…'@` через `powershell -Command "..."` из чата.
- **Что пошло не так:** парсер PowerShell 5.1 некорректно интерпретировал границы here-string, ломался на первом же переводе строки внутри блока. Ошибка выглядела как `CommandNotFoundException` на случайных фрагментах текста.
- **Корневая причина:** ограничение PS 5.x — `@'…'@` внутри аргумента `-Command` парсится до раскрытия строки, кавычки конфликтуют. В PS 7.x проблема частично снята, но целевая среда пользователя — 5.1.
- **Правило на будущее:** любой скрипт длиннее 5 строк или содержащий here-strings записывается в файл через `code scripts/<name>.ps1`, затем запускается как `powershell -ExecutionPolicy Bypass -File scripts\<name>.ps1`. В чате передавать только однострочные команды разведки (диагностика, чтение).
- **Как проверить:** в ответе ассистента нет блоков вида `powershell -Command "@'`. Все скрипты вызываются через `-File`.
- **Связанные файлы:** `scripts/normalize_nervous_system_v1.ps1`.

### L-055-01 — Не обрезать строки со списками файлов через Substring

- **Дата:** 2026-08-05
- **Сессия:** Session 55 (Этап F.2 — EBM-обогащение female_hormones.md, закрытие сессии)
- **Контекст:** при построении патча I1 для `v2/SOURCES_INDEX.md` строка со списком FULL_EBM-файлов была прочитана через `Substring(0, 160)` для превью в разведке.
- **Что пошло не так:** обрезка урезала строку ровно на границе пробела после запятой (`nervous_system.md`,`nutraceuticals.md` вместо `nervous_system.md`, `nutraceuticals.md`). Патч был построен под обрезанную версию, `-replace` не нашёл совпадения в реальном файле, скрипт `close_session55.ps1` упал на I1 до записи STATUS.md. Пришлось делать второй скрипт `fix_status_session55.ps1`, в git появились два коммита закрытия вместо одного.
- **Корневая причина:** превью для человека использовалось как источник истины для построения патча. Substring теряет пробелы и любые незаметные глазу символы.
- **Правило на будущее:** для построения строк патча ВСЕГДА использовать полную строку (`$_.Line` в Select-String, `[System.IO.File]::ReadAllText`), а не превью. Превью с `Substring` допустимо только для вывода человеку с явной пометкой `(preview, truncated)`. Если строка длиннее 120 символов и содержит список — извлекать её через regex-anchor: `[regex]::Match($text, 'FULL_EBM — \d+ файлов.+?\.').Value`.
- **Как проверить:** в скриптах отсутствуют вызовы `Substring(...)` в блоках построения `$old`/`$new` для `-replace`. Разрешён только в блоках `Write-Host` для превью с суффиксом `...`.
- **Связанные файлы:** `scripts/close_session55.ps1` (сломанный), `scripts/fix_status_session55.ps1` (исправление), `v2/SOURCES_INDEX.md`.

### L-056-01 — Пороги аудита проверять в Шаге 0 разведки

- **Дата:** 2026-08-05
- **Сессия:** Session 56 (Этап F.2 — EBM-обогащение covid_pregnancy.md)
- **Контекст:** цель сессии из STATUS.md — «16 → 25 тегов, +9 inline». Скрипт отработал чисто, файл проставлен как FULL_EBM в метаданных, все 15 валидаций зелёные. Аудит-скрипт `scripts/audit_ebm_compliance.ps1` при этом оставил файл в PARTIAL_EBM.
- **Что пошло не так:** файл технически FULL_EBM (маркер, статус, 25 тегов, метаданные — всё правильно), но аудит-скрипт использует критерий `$hasMarker -and $ebmTags -ge 30`. Порог 30, а не 25. Пришлось делать второй проход `normalize_covid_pregnancy_v2.ps1` (+5 тегов до 30), второй коммит обогащения не понадобился (объединили в один по playbook-инварианту), но время потеряно на непредвиденный второй проход.
- **Корневая причина:** playbook Шаг 0 «Идентификация цели» не включал сверку с `scripts/audit_ebm_compliance.ps1` или `project/EBM_STANDARD.md`. Цель бралась из блока «Следующая сессия» в STATUS.md, где число 25 было выбрано «на глаз» ещё в Session 55. Порог 30 в аудите — жёсткий, а мы его не проверяли.
- **Правило на будущее:** в Шаге 0 playbook `session_ebm_enrichment.md` обязательно открывать `scripts/audit_ebm_compliance.ps1` и извлекать порог FULL_EBM (`$ebmTags -ge N`). Целевое число тегов сессии = `max(N, план из STATUS.md) + буфер 2-3`. Если в STATUS.md записано число < порога — исправить STATUS.md до старта сессии, не после.
- **Как проверить:** в Шаге 0 присутствует одна команда, извлекающая порог: `Select-String -Path scripts/audit_ebm_compliance.ps1 -Pattern 'ebmTags -ge \d+'`. Целевое число тегов сессии не меньше найденного порога.
- **Связанные файлы:** `scripts/audit_ebm_compliance.ps1` (порог на L51), `project/PLAYBOOKS/session_ebm_enrichment.md` (Шаг 0), `scripts/normalize_covid_pregnancy_v1.ps1` (первый проход), `scripts/normalize_covid_pregnancy_v2.ps1` (доборный проход).

### L-056-02 — Первое добавление маркера ≠ замена: guard идемпотентности учитывает оба случая

- **Дата:** 2026-08-05
- **Сессия:** Session 56 (Этап F.2 — EBM-обогащение covid_pregnancy.md)
- **Контекст:** covid_pregnancy.md был обогащён в Session 40 «вручную» (без normalize-скрипта), поэтому маркер `<!-- EBM_ENRICHED_vX.Y -->` в файле полностью отсутствовал. В vitamins/nervous_system/female_hormones он всегда был — обогащение шло по схеме v1.1 → v1.2.
- **Что пошло не так:** ничего критичного, но потребовалось поймать нюанс на этапе планирования — патч M5 добавлял маркер **впервые** (Insert перед `## Метаданные`), а не заменял старый (Replace). В шаблоне normalize-скрипта из предыдущих сессий все M-патчи были Replace, что для этого файла бы упало на «якорь не найден».
- **Корневая причина:** playbook неявно предполагал, что каждый PARTIAL_EBM файл уже прошёл через normalize-скрипт хотя бы раз, значит маркер есть. Для файлов, обогащённых вручную до появления скриптов (Sessions 38-40), это не так.
- **Правило на будущее:** в Шаге 1 разведки playbook обязательно проверять наличие маркера `<!-- EBM_ENRICHED_v` в файле. Если маркера нет — в скрипте нормализации использовать **Insert-перед-`## Метаданные`**, а не Replace. Если маркер есть — Replace с указанием предыдущей версии. Guard идемпотентности одинаковый в обоих случаях (проверка новой версии маркера).
- **Как проверить:** в Шаге 1 присутствует строка вывода `Marker present: yes/no`. В normalize-скрипте комментарий над M-патчем маркера указывает тип операции: `# M5 — Insert (маркер отсутствовал)` или `# M5 — Replace vX.Y -> vX.Z`.
- **Связанные файлы:** `scripts/normalize_covid_pregnancy_v1.ps1` (M5 — Insert), `scripts/normalize_female_hormones_v1.ps1` (M5 — Replace, для сравнения), `project/PLAYBOOKS/session_ebm_enrichment.md` (Шаг 1).

### L-057-01 — PowerShell: markdown-бэктики в якорях требуют single quotes

**Дата**: 2026-08-05
**Сессия**: 57 (закрытие, close_session57.ps1)
**Контекст**: Скрипт `close_session57.ps1` при первом запуске упал на [S2] с "ANCHOR NOT FOUND". Якорная строка содержала markdown-обрамление `` `covid_pregnancy.md` ``. В скрипте якорь был записан в двойных кавычках PowerShell: `$s2old = "... `covid_pregnancy.md` ..."`.

**Проблема**: В PowerShell двойные кавычки — интерполируемая строка, а бэктик `` ` `` — escape-символ (например, `` `n `` = newline, `` `t `` = tab). Внутри `"..."` последовательность `` `c `` не escape (буква не спецсимвол), но парсер PowerShell **всё равно съедает бэктик** как escape-префикс, оставляя саму букву. В результате в переменной `$s2old` оказалась строка **без бэктиков** — `covid_pregnancy.md` вместо `` `covid_pregnancy.md` ``. Поиск такой строки в файле, где реально есть `` `covid_pregnancy.md` `` с бэктиками, не находил совпадений → ANCHOR NOT FOUND.

**Корневая причина**: якорные строки для `.Replace()` строились в двойных кавычках PowerShell при наличии markdown-разметки с бэктиками. Двойные кавычки + бэктик = ловушка.

**Правило на будущее**: Все якорные строки в normalize- и close-скриптах, содержащие **любые из символов** `` ` ``, `$`, `"`, писать **в одинарных кавычках** `'...'` (literal-строки, PowerShell не интерпретирует ничего). Для многострочных якорей — использовать конкатенацию через `+ "`n" +` только для перевода строки, сам контент — в single quotes.

**Верификация**: После исправления скрипт `close_session57.ps1 v2` отработал 19 патчей + 23 валидации без единой ошибки.

**Смежные уроки**:

- L-053-01 (транзакционность) — сработала: при FAIL до Write файл не изменился.
- L-054-01 (нет here-strings) — не нарушено.
- L-055-01 (полные строки, не Substring) — не нарушено; ошибка была в кодировании кавычек, не в подстроках.

**Файлы**:

- `scripts/close_session57.ps1` (исправленная версия)
- `project/PLAYBOOKS/session_ebm_enrichment.md` — обновить Шаг 4 (правила кодирования якорей)
- `project/LESSONS.md` — эта запись

### L-058-01 — обязательная таблица «патч → +тегов» до отправки normalize-скрипта

**Дата**: 2026-08-06
**Сессия**: 58 (normalize_pancreas_health_v1.ps1)

**Контекст**: скрипт v1 pancreas_health.md был отправлен пользователю с заявленной целью «30 EBM-тегов». По факту содержал 32 патча, каждый добавляющий 1 тег: 30 обычных (заголовок += тег) + 2 вставки блоков с тегами. При запуске упал на P6 из-за неверной логики «корректировочных патчей»: P6 искал якорь с уже вставленным тегом Tenner 2013 в заголовке §5, которого не существовало — тег ушёл в inline-блок перед §5, а не в сам заголовок.

**Проблема**: подсчёт тегов делался «на глаз» при 30+ патчах. Разница между «заголовок += тег» (+1) и «вставка блока с тегом» (+1) при разных якорях создаёт когнитивную нагрузку, где легко ошибиться на 1-2.

**Корневая причина**: отсутствие явного пре-flight пересчёта тегов в структурированной таблице.

**Правило**: перед отправкой любого normalize-скрипта пользователю ассистент обязан построить в своём ответе markdown-таблицу с колонками P№, Секция, Действие, +тегов, где каждый патч имеет явное количество добавляемых тегов, и убедиться, что сумма колонки +тегов равна целевому числу из плана. Если сумма не равна target — план правится ДО отправки, а не после падения скрипта.

**Верификация**: скрипт v2 pancreas_health.md был построен с явной таблицей (см. сообщение в чате Session 58), убраны P10 и P17 для точного попадания в 30 → прогон 30/30 патчей + 29/29 валидаций OK с первого раза.

**Смежные уроки**: L-053-01 (транзакционность), L-054-01 (создание скриптов через code), L-055-01 (полные строки для replace), L-057-01 (single quotes для якорей).

**Связь с TECH_DEBT**: TD-005 (методологический долг: интеграция правила в playbook Шаг 3).

**Файлы**: scripts/normalize_pancreas_health_v1.ps1 (v2 — успех), project/LESSONS.md (эта запись), project/TECH_DEBT.md (TD-005), в будущем project/PLAYBOOKS/session_ebm_enrichment.md (v1.1 → v1.2).

### L-059-01 — Не использовать markdown-таблицы и тройные бэктики в теле PowerShell-скриптов для чата

- **Дата:** 2026-08-09
- **Сессия:** Session 58 (Этап F.2 — хвост, tech-debt cleanup)
- **Контекст:** при генерации normalize-скрипта pancreas_health.md v1 внутри тела скрипта была markdown-таблица patch→tags; при генерации update_tech_debt_and_lessons_s58.ps1 внутри тела были блоки с тройными бэктиками для примеров команд.
- **Что пошло не так:** внешний markdown code-block чата закрывался преждевременно на первой последовательности из трёх бэктиков внутри тела скрипта; пользователь получал разорванный скрипт, вынужден был просить "дай в одном окне чтобы я только скопировала" дважды за одну сессию.
- **Корневая причина:** рендерер чата не поддерживает вложенные fenced code-blocks; тройные бэктики закрывают внешний блок независимо от контекста PowerShell here-string. Markdown-таблицы визуально ломают монотонность скрипта и мешают копированию.
- **Правило на будущее:** при генерации PowerShell-скриптов в чат — тело скрипта НЕ должно содержать ни ` ``` `, ни markdown-таблиц `| … |`. Все пояснительные таблицы (patch→tags, ожидаемые метрики, план валидаций) выносятся в сообщение ДО блока со скриптом. Внутри скрипта — только plain-text комментарии `# comment` и ASCII-разделители `# ---`. Примеры команд в комментариях — без бэктиков.
- **Как проверить:** перед отправкой скрипта в чат — grep тела на `\x60\x60\x60` (тройной бэктик) и на `| ` (пайп с пробелом, признак markdown-таблицы). Если найдено — переписать без них.
- **Связанные файлы:** `scripts/normalize_pancreas_health_v1.ps1` (первое проявление), `scripts/update_tech_debt_and_lessons_s58.ps1` (второе проявление), `project/TECH_DEBT.md` (TD-006).
