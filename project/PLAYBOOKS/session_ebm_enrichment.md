# PLAYBOOK: EBM-обогащение методологического файла

**Тип сессии:** структурная нормализация одного файла из `references/methodology/` со статусом PARTIAL_EBM → FULL_EBM.

**Когда использовать:** каждая сессия вида «поднять файл X до FULL_EBM» (Session 53 vitamins, Session 54 nervous_system, Session 55 female_hormones — все прошли по этому шаблону).

**Прочитать перед стартом:** `project/STATUS.md` (текущая сессия), последние 3 записи `project/LESSONS.md`, этот файл целиком.

**Целевой результат сессии:**

- Файл-цель имеет ≥30 inline тегов `[EBM: ...]`, статус FULL_EBM, обновлённый маркер `<!-- EBM_ENRICHED_vX.Y -->`.
- STATUS.md и SOURCES_INDEX.md обновлены до нового маркера vN+1.
- Ровно один git-коммит на обогащение файла + ровно один git-коммит на закрытие сессии.

---

## Шаг 0 — Идентификация цели

Из `project/STATUS.md` в блоке «Следующая сессия» взять:

- имя файла-цели (например, `covid_pregnancy.md`);
- текущее количество EBM-тегов;
- целевое количество (обычно текущее + 5-8, минимум 30).

Если цель не указана — не начинать сессию, попросить пользователя уточнить.

## Шаг 1 — Разведка (read-only, однострочный PS)

Однострочная команда в PowerShell (передаётся пользователю целиком, в одной рамке). Собирает: размер файла, наличие BOM, число тегов `[EBM:`, все маркеры `<!-- ... -->`, все H2-заголовки, последние 30 строк (метаданные).

**Правило L-054-01:** только однострочная команда. Никаких `@'…'@` в аргументе `-Command`.

**Правило L-055-01:** для превью длинных строк использовать суффикс `... (preview)`. Не строить патчи на основе превью.

## Шаг 2 — Распределение тегов по H2-секциям

Вторая однострочная разведочная команда — считает EBM-теги по каждой H2-секции. Показывает, где инлайн-тегов нет (кроме §Источники).

Выбрать 5-8 клинически плотных секций для вставки новых тегов. Приоритет — секции с 0 тегов и высокой клинической плотностью (диагностика, дозировки, критерии).

## Шаг 3 — План патчей

Составить таблицу из двух блоков:

**EBM-патчи (P1..P8):**

- номер, секция, якорная фраза (полная, не превью), какой источник цитируется.
- Источники — из §Источники того же файла (не выдумывать).

**Метаданные (M1..M5):**

- M1: version bump (v2.1 → v2.2).
- M2: дата последнего обновления + номер сессии.
- M3: запись в «Историю версий».
- M4: статус EBM-lite/PARTIAL_EBM → FULL_EBM.
- M5: маркер `<!-- EBM_ENRICHED_vX.Y -->` → новая версия.

Показать план пользователю до создания скрипта. Ждать подтверждения.

## Шаг 4 — Скрипт normalize (транзакционный)

Создать файл `scripts/normalize_<название>_v1.ps1` через `code scripts/normalize_<название>_v1.ps1`.

**Правило L-053-01 — жёсткая структура скрипта:**

    # === GUARD ===
    if ($content -match '<!-- EBM_ENRICHED_vX.Y -->') { Write-Host "Уже обогащён, выход"; exit 0 }

    # === BACKUP ===
    Copy-Item $path "$path.bak.$(Get-Date -Format 'yyyyMMdd-HHmmss')"

    # === READ ===
    $content = [System.IO.File]::ReadAllText($path, [System.Text.Encoding]::UTF8)

    # === APPLY ===
    # P1..P8, M1..M5 — все патчи применяются к $content в памяти

    # === VALIDATE ===
    $checks = @( ... )   # минимум 13 проверок: BOM, ≥30 тегов, версия, маркеры, размер
    $failed = $checks | Where-Object { -not $_.Ok }
    if ($failed) { Write-Host "Валидация провалена"; exit 1 }

    # === WRITE ===
    # Set-Content вызывается ТОЛЬКО здесь, ТОЛЬКО если валидация прошла

Обязательные проверки в блоке VALIDATE:

1. BOM сохранён.
2. Число тегов ≥30 и совпадает с ожидаемым.
3. Новая версия присутствует в метаданных.
4. Старая версия из метаданных удалена.
5. Новый маркер `<!-- EBM_ENRICHED_vX.Y -->` присутствует.
6. Старый маркер отсутствует.
7. Статус FULL_EBM присутствует, EBM-lite удалён.
8. Размер файла увеличился (не уменьшился).
   9-13. Проверки на присутствие конкретных цитат (по одной на каждый P-патч).

### ⚠️ Ловушка PowerShell (L-057-01)

Если якорная строка содержит markdown-бэктики (например, имя файла в обратных кавычках), **всегда** оборачивай её в **single quotes** (одинарные кавычки), а не в double quotes.

Причина: в double-quoted строке PowerShell бэктик — это escape-префикс, он исчезает из строки, и `-replace` не находит якорь → `ANCHOR NOT FOUND`.

Плохо (бэктики съедаются):

    $anchor = "- `covid_pregnancy.md` (обогащён)"   # бэктики исчезнут

Хорошо (литерал сохраняется):

    $anchor = '- `covid_pregnancy.md` (обогащён)'   # бэктики на месте

Для многострочных якорей — конкатенация single-quoted литералов или here-string на одинарных кавычках.

Инцидент: close_session57.ps1 v1 упал на [S2] из-за escape-эффекта → фикс v2 через single quotes → 19 патчей + 23 валидации зелёные.

## Шаг 5 — Прогон и валидация

Запуск: `powershell -ExecutionPolicy Bypass -File scripts\normalize_<...>_v1.ps1`.

Пользователь присылает вывод. Проверить:

- backup создан;
- все P- и M-патчи применились (✓);
- 13/13 валидаций зелёные;
- размер изменился на ожидаемую величину (±20%).

Если хоть одна проверка красная — не идти дальше. Диагностировать, чинить скрипт, перезапускать (guard идемпотентности не даст сломать файл).

## Шаг 6 — Аудит проекта

Запустить `scripts/audit_ebm_compliance.ps1` через `Select-String` по паттерну сводки. Убедиться:

- FULL_EBM +1 файл;
- PARTIAL_EBM –1 файл;
- Общее число тегов выросло на ожидаемую дельту.

## Шаг 7 — Коммит обогащения

Одна команда, одна рамка:

    git add references/methodology/<файл>.md;
    git --no-pager diff --cached --stat;
    git commit -m "feat(methodology): <файл>.md PARTIAL_EBM -> FULL_EBM (Session N) — +K inline EBM-тегов, vX.Y -> vX.Z";
    git push origin main;
    git --no-pager log --oneline -5

Ожидаемый diff: ~13 insertions / ~12 deletions на файл.

## Шаг 8 — Закрытие сессии

Создать `scripts/close_session<N>.ps1` через `code`. Скрипт по той же схеме Read → Apply → Validate → Write, но применяется к двум файлам: `project/STATUS.md` и `v2/SOURCES_INDEX.md`.

**Правило L-055-01 — критично для этого шага:** списки FULL_EBM/PARTIAL_EBM файлов в SOURCES_INDEX.md — длинные строки. Патчи для них строить ТОЛЬКО через полную строку (`[regex]::Match($text, 'FULL_EBM — \d+ файлов.+?\.').Value`), НИКОГДА через `Substring`.

Патчи STATUS.md (S1..S10):

- обновить блок «Последнее событие»;
- метрики: FULL_EBM count и %, PARTIAL_EBM count и %;
- Всего EBM-тегов: старое → новое;
- следующая сессия N+1: цель;
- запись в историю сессий с ссылкой на коммит из Шага 7;
- маркер `<!-- STATUS_SESSION<N-1>_APPLIED -->` → `<!-- STATUS_SESSION<N>_APPLIED -->`.

Патчи SOURCES_INDEX.md (I1..I4):

- список FULL_EBM (добавить файл, обновить count);
- список PARTIAL_EBM (убрать файл, обновить count);
- сводка: `Всего: <tags> тегов, <lines> строк (updated Session <N>)`;
- маркер `<!-- SOURCES_INDEX_EBM_APPLIED_v<N-1> -->` → `<!-- SOURCES_INDEX_EBM_APPLIED_v<N> -->`.

Ожидаемое число валидаций: 18 (11 для STATUS.md + 4 для SOURCES_INDEX + 3 общих).

## Шаг 9 — Коммит закрытия

    git add project/STATUS.md v2/SOURCES_INDEX.md scripts/normalize_*.ps1 scripts/close_session<N>.ps1;
    git --no-pager diff --cached --stat;
    git commit -m "docs(status): закрытие Session <N> — <файл>.md PARTIAL->FULL_EBM, метрики <F>/53 FULL, <P> PARTIAL, +<K> EBM-тегов; маркеры v<N-1>->v<N>";
    git push origin main

## Шаг 10 — Ретроспектива

Если в сессии была ошибка, которая стоила времени (например, скрипт упал на середине, пришлось делать fix\_-скрипт) — обязательно добавить запись в `project/LESSONS.md` по шаблону оттуда. Не откладывать на потом.

Если сессия прошла чисто — коротко зафиксировать в ответе пользователю: «Session N закрыта, коммит <hash>, метрики <...>, уроков не добавлено».

## Инварианты (нарушать нельзя)

1. Один normalize-скрипт = один методологический файл. Не пакетить несколько файлов в один скрипт.
2. Один коммит на обогащение + один коммит на закрытие. Не смешивать.
3. Каждый скрипт — транзакционный по схеме L-053-01.
4. Все скрипты создаются через `code scripts/<name>.ps1` (L-054-01), не через `-Command`.
5. Строки для `-replace` — только полные, никогда через `Substring` (L-055-01).
6. Guard идемпотентности в начале каждого скрипта — обязателен.
7. Якорные строки с markdown-бэктиками, знаками доллара или двойными кавычками — только в single quotes (L-057-01). Double quotes + backtick = escape-ловушка.

## Invariant 8: Побайтная валидация якорей до отправки скрипта

Перед составлением `$Old` в `Apply-Patch` — обязательный вывод целевых строк из файла и побайтная сверка с текстом якоря:

    $line = (Get-Content $file -Encoding UTF8)[N-1]
    Write-Host "Contains anchor: $($line.Contains($anchor))"

Для якорей с Unicode-символами (стрелки →, тире —, буллеты •) — дополнительно вывести коды каждого символа в контексте якоря. Не полагаться на визуальное совпадение: пробел U+0020, неразрывный пробел U+00A0 и артефакты Write-Host в узкой консоли выглядят одинаково.

**Rationale:** L-057-01 (single quotes) закрывает интерпретацию бэктиков, но не решает проблему пробелов вокруг Unicode. Session 59 — три инцидента якорей (S1, S9, P28), суммарно ~15 минут потерь.

**Related lessons:** L-057-01, TD-010.

## Invariant 9: UTF-8 BOM для скриптов + пороги размера по факту

**9a. Кодировка PS-скриптов.** Все скрипты сохранять только с `UTF-8 with BOM`. При записи из PS — `Set-Content -Encoding UTF8` или `UTF8Encoding($true)`. Запрещено: `UTF8Encoding($false)` — Windows PowerShell 5.1 читает без BOM как cp1251, кириллица → mojibake, скрипт не парсится.

**9b. Пороги валидации размера.** Первый запуск скрипта — «сухой» с порогом +50 chars для сбора реальной дельты. Финальный порог = 50–70 % от факта (запас 20–30 %). Для метафайлов (SOURCES_INDEX, STATUS), где патчи могут сокращать — использовать `[Math]::Abs($delta) -ge N`.

**Rationale:** TD-008 (BOM) и TD-009 (пороги) — по 15 и 10 минут потерь в Session 59.

**Related lessons:** L-059-02, L-059-03. Related tech debt: TD-008, TD-009.
