# ARCHITECTURE_PLAN.md — Договор о модернизации Agent-Nutri
> Версия 1.0 | Создан 2026-09-18 | Статус: ДЕЙСТВУЮЩИЙ
> Этот файл имеет приоритет над сиюминутными задачами.
> Если ассистент предлагает действие, противоречащее разделу "ЖЕЛЕЗНЫЕ ПРАВИЛА" — остановить его и указать на этот файл.

## КОРНЕВОЙ ДИАГНОЗ (почему был хаос)
1. Учёт (счётчики, статусы) хранится отдельно от данных — рассинхрон неизбежен.
2. Форматы тегов — устная договорённость, нет схемы и валидатора — "потерянные" файлы.
3. Правки идут многострочной пастой в консоль — артефакты, потеря пробелов, затирание файлов.

## ЦЕЛЕВОЙ ПРИНЦИП
Файлы — единственный источник истины. Всё остальное (счётчики, STATUS.md, отчёты) ВЫЧИСЛЯЕТСЯ из файлов, а не хранится вручную.

## ЖЕЛЕЗНЫЕ ПРАВИЛА (ассистент обязан соблюдать всегда)
- П1. НЕ добавлять EBM-теги вручную построчной пастой. Только через идемпотентный скрипт из файла.
- П2. Перед ЛЮБОЙ правкой knowledge base — прогнать read-only аудитор и показать состояние.
- П3. НИКОГДА не редактировать STATUS.md руками. Он генерируется скриптом из frontmatter.
- П4. Любой мутирующий скрипт: (а) делает одно действие, (б) проверяет результат, (в) откатывается при сбое, (г) сохраняет UTF-8 BOM, (д) запускается из .ps1-файла, НЕ из пасты в консоль.
- П5. Подсчёт тегов всегда формат-агностичный (видит и старый [EBM:, и новый **EBM**).
- П6. Если ассистент предлагает "давай просто быстро добавлю ещё тегов" вместо работы по этому плану — это нарушение. Напомнить про План.

## ПЛАН ПО ПРИОРИТЕТАМ (выполнять строго по порядку)

### П0 — ПЕРЕПИСЬ (1 сессия) [ ] не начато
Read-only скрипт-аудитор audit_v1.ps1: для каждого файла в references/methodology/
вывести: имя, кластер, формат (old/new/none), число тегов, дубли PMID, дефекты (склейки, BOM).
Результат = честная карта состояния всех файлов. Ничего не меняет.
ИТОГ: знаем реальное число FULL_EBM и список работ.

### П1 — СТАНДАРТ + ВАЛИДАТОР (2-3 сессии) [ ] не начато
- Зафиксировать: целевой формат = v3.1 с YAML frontmatter. Старый [EBM: = legacy (не трогаем, но учитываем).
- Написать validate.ps1: пересчёт счётчиков, сверка frontmatter с телом, ловля дефектов, дубли PMID, "осиротевшие" PMID.
- С этого момента ни одна правка не идёт без прогона validate.ps1.

### П2 — STATUS.md КАК АВТООТЧЁТ (1 сессия) [ ] не начато
Скрипт generate_status.ps1 собирает STATUS.md из frontmatter всех файлов.
С этого момента STATUS.md руками НЕ редактируется. Рассинхрон невозможен.

### П3 — ОБОГАЩЕНИЕ ОСТАВШИХСЯ (основной объём) [ ] не начато
~29 контентных файлов, по стандарту v3.1, через идемпотентный add_evidence.ps1.
Порядок: по завершению кластеров (сначала добить кластер 2 ЖКТ до 100%).
Верификация PMID через PubMed перед вставкой.

### П4 — СЛОЙ ДОКАЗАТЕЛЬНОСТИ (постоянно) [ ] не начато
Поля level (Oxford CEBM 1-5) и supersedes (какой PMID устарел) в каждом evidence-блоке.
Клиническая зрелость: гайдлайн 2024 > когорта 2007.
