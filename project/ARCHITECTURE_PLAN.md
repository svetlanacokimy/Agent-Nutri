## КОРНЕВОЙ ДИАГНОЗ (почему был хаос)
1. Учёт (счётчики, статусы) хранится отдельно от данных — рассинхрон неизбежен.
2. Форматы тегов — устная договорённость, нет схемы и валидатора — "потерянные" файлы.
3. Правки идут многострочной пастой в консоль — артефакты, потеря пробелов, затирание файлов.

## ЦЕЛЕВОЙ ПРИНЦИП
Файлы — единственный источник истины. Всё остальное (счётчики, STATUS.md, отчёты) ВЫЧИСЛЯЕТСЯ из файлов, а не хранится вручную.

## ЖЕЛЕЗНЫЕ ПРАВИЛА (ассистент обязан соблюдать всегда)
- П1. НЕ добавлять EBM-теги вручную построчной пастой. Только через идемпотентный скрипт из файла.
- П2. Перед ЛЮБОЙ правкой knowledge base — прогнать read-only аудитор и показать состояние.
- П3. НИКОГДА не редактировать STATUS.md руками. Он генерируется скриптом из frontmatter.
- П4. Любой мутирующий скрипт: (а) делает одно действие, (б) проверяет результат, (в) откатывается при сбое, (г) сохраняет UTF-8 BOM, (д) запускается из .ps1-файла, НЕ из пасты в консоль.
- П5. Подсчёт тегов всегда формат-агностичный (видит и старый [EBM:, и новый **EBM**).
- П6. Если ассистент предлагает "давай просто быстро добавлю ещё тегов" вместо работы по этому плану — это нарушение. Напомнить про План.

## АРХИТЕКТУРНЫЕ РЕШЕНИЯ
- Р1 (2026-09-18): Целевой формат тегов = v3.1 (**EBM** + YAML frontmatter, уровни CEBM). Старый формат [EBM: PMID:] остаётся в 15 рабочих файлах как legacy — НЕ переписываем сейчас (риск без пользы). Новые и дообогащаемые файлы — только v3.1.
- Р2 (2026-09-18): "Один PMID несколько раз" НЕ является дефектом, если это РАЗНЫЕ утверждения в РАЗНЫХ секциях (пример: NAMS 2022 PMID:35797481 законно стоит в 5 секциях menopause). Дубль = один PMID дважды в ОДНОМ утверждении. Валидатор считает дубли по паре "PMID+утверждение", а не по PMID глобально.
