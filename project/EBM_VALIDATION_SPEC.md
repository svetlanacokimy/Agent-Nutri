# EBM_VALIDATION_SPEC.md — Спецификация валидатора knowledge base
> Версия 1.0 | 2026-09-18 | Основание: ARCHITECTURE_PLAN.md, приоритет П1
> Это ЧТО проверяет validate.ps1. Сам скрипт пишется под эту спецификацию.

## Термины
- ТЕГ (old): подстрока вида `[EBM: ... PMID:NNNNNNN]`.
- ТЕГ (new v3.1): подстрока вида `**EBM** [Level N, ...]`.
- УТВЕРЖДЕНИЕ: одна строка markdown, к которой прикреплён тег.
- PMID: число 5-9 цифр после `PMID:`.

## Проверки (каждая = отдельный вердикт PASS/FAIL)

### C1. BOM
Первые 3 байта файла = EF BB BF. FAIL если нет.

### C2. Склейки
Не должно быть буквы вплотную к открытию тега: паттерн `[а-яёa-zА-ЯЁA-Z]\[EBM:`. Норма = 0 совпадений.

### C3. Осиротевшие old-теги
Каждый `[EBM:` должен содержать `PMID:` до закрывающей `]`. Тег без PMID = FAIL (источник не указан).

### C4. Дубль PMID в одном утверждении (правило Р2)
Один и тот же PMID дважды в ОДНОЙ строке = FAIL.
Один PMID в РАЗНЫХ строках/секциях = НОРМА (не дефект). Пример нормы: NAMS 2022 PMID:35797481 в 5 секциях menopause.

### C5. Соответствие статуса числу тегов
FULL заявляется при >=30 тегах. Если файл помечен FULL, но тегов <30 (или наоборот) — предупреждение (WARN), не критично.

### C6. Незакрытый тег
Каждый `[EBM:` имеет парную `]` в той же строке. Незакрытый = FAIL.

## Коды выхода валидатора
- 0 — все проверки PASS (база здорова, можно вносить правки).
- 1 — есть хотя бы один FAIL (правки запрещены до устранения).
- WARN не блокирует, но выводится в отчёт.

## Принцип использования
Перед любым мутирующим скриптом (add_evidence.ps1 и т.п.) — сначала validate.ps1.
Если код выхода != 0 — СТОП, не редактировать.
