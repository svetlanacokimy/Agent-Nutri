# Соглашения для файлов методологии (Agent-Nutri)

> **Назначение**: единые правила работы и оформления, чтобы файлы оставались согласованными между сессиями. Перед любым изменением в `references/methodology/` — открыть этот файл и сверить.

---

## 1. Правила работы (process)

### 1.1. Распределение инструментов ⭐

| Когда | Инструмент |
|-------|------------|
| Маленькие правки строк через `.Replace()`, поиск, аудит, метрики | PowerShell (терминал VS Code или сервера) |
| Git операции (add/commit/push/status/diff) | PowerShell |
| Запуск `.ps1` скриптов из `scripts/` | PowerShell |
| Создание новых файлов более 100 строк | Cline |
| Большая реструктуризация существующего файла | Cline |
| Сложные markdown с таблицами, кавычками, спецсимволами | Cline |

### 1.2. Запрещённые практики ⚠️

- ❌ Блокнот (notepad.exe) для редактирования methodology-файлов
- ❌ Передача в PowerShell консоль команд длиннее ~2000 символов (paste-buffer ломается, here-string зависает на `>>`)
- ❌ Многострочные here-strings (`@'...'@`) с тройными кавычками или со спецсимволами внутри
- ❌ Изменение номеров параграфов (см. §2)
- ❌ Коммит без аудита ссылок (см. §1.4)

### 1.3. Workflow для существенной правки ⭐

1. **Backup** перед серией правок: `Copy-Item file.md file.md.backup_sessNN_partX`
2. **Изменение** через правильный инструмент (PowerShell или Cline по §1.1)
3. **Аудит ссылок**: `& scripts\audit_links.ps1` — должно быть `Broken: 0`
4. **Метрики**: подсчёт строк, H2, H3, маркеров
5. **Git**: add → commit (с подробным сообщением) → push
6. **Удаление backup** после успешного push

### 1.4. Сессии и STATUS

- В конце каждой сессии — обновление `project/STATUS.md`
- Большие задачи разбиваются на Part A / Part B / Part C, каждая Part = отдельный коммит

## 2. Правила нумерации параграфов

### 2.1. Принцип неизменной нумерации ⭐

- Номера H2-параграфов (`## N. Название`) — **стабильные идентификаторы**, как ID в базе данных
- При удалении параграфа номер **не переиспользуется**, в файле остаётся «дыра» — это нормально
- **Пример**: `liver_health.md` §§8, 9 удалены — после §7 сразу идёт §10
- При добавлении нового раздела — следующий свободный номер в конце файла

### 2.2. Что можно и что нельзя

| Действие | Разрешено? |
|----------|------------|
| Переименовать заголовок раздела | ✅ Да |
| Изменить содержимое раздела | ✅ Да |
| Удалить раздел (оставив дыру) | ✅ Да |
| Добавить новый раздел в конце | ✅ Да |
| Перенумеровать существующие разделы | ❌ Нет (ломает входящие ссылки) |
| Переиспользовать номер удалённого раздела | ❌ Нет (создаёт семантически битые ссылки) |

---

## 3. Правила кросс-ссылок

### 3.1. Единый формат ⭐

**Канонический**:
- `liver_health.md §21` — один раздел
- `liver_health.md §§12, 13` — несколько
- `liver_health.md §§7, 10–12` — диапазон с учётом дыр

**Допустимо (legacy)**: `liver_health.md раздел 21`, `liver_health.md разделы 12 и 13`

**Запрещено ⚠️**:
- Диапазоны через дыры без перечисления (`разделы 7–12` при отсутствующих §§8, 9 → правильно `§§7, 10–12`)
- Ссылки без номера, когда контекст требует точности

### 3.2. Семантическая проверка

Технический аудит проверяет существование §N, но не смысл. Перед коммитом открыть целевой §N и сверить с контекстом ссылки.

## 4. Маркеры (legend) ⭐

| Маркер | Значение | Когда ставить |
|--------|----------|---------------|
| ⭐ | Сильная рекомендация, доказательная база | Основные протоколы, RCT, ключевые правила |
| ◆ | Контекст, упоминание, спорная зона | Дополнительная информация, развивающаяся база |
| ⚠️ | Стоп / врач / противопоказание | Red flags, контраиндикации, направление к врачу |

Маркеры ставятся в заголовке раздела или в начале строки списка. Возможна комбинация: `## 15. Барьер ⭐⚠️`.

## 5. Структура файла methodology

```markdown
# Название файла
> Краткое описание + связанные протоколы

## Связанные документы
- `файл1.md` — описание

## 1. Раздел один ⭐
### 1.1. Подраздел

## 2. Раздел два
...

## N. Источники

## Метаданные
```

- **H1** — только название файла (1 раз)
- **H2** — нумерованные `## N. Название` + служебные (Связанные документы, Источники, Метаданные)
- **H3** — формат `### N.M. Название`
- **Готовый шаблон:** `_template.md` — копировать для создания нового протокола

---

## 6. Двухслойная архитектура

- **Слой 1 — учебник**. Линейные файлы по органам/системам. Внутри — три части: Part A (теория), Part B (протоколы), Part C (навигация).
- **Слой 2 — навигация**. `_conventions.md` (этот файл), `routing_map.md` (планируется), `marker_legend.md` (включён в §4).

## 7. Backup-файлы

- **Имя**: `файл.md.backup_sessNN_partX`
- После успешного push — удалить
- В git не коммитятся
