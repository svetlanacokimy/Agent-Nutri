CLAUDE.md — Брифинг для Cline / Claude Code
Этот файл читается агентом первым при старте любой задачи в этом репозитории. Он НЕ дублирует другие файлы. Он маршрутизирует к ним.

Что это за проект
Agent-Nutri Pro — клинический нутрициологический агент. По данным пациента (анализы, профиль, жалобы) генерирует профессиональную консультацию в двух стилях: EXPERT (для нутрициолога) и CLIENT (для пациента).

Главный пользователь — практикующий нутрициолог. Каждый промах в логике или цифрах = реальный риск для пациента. Работать аккуратно.

Точка входа при любой команде
Перед выполнением ЛЮБОЙ команды пользователя прочитай в таком порядке:

v2/HIERARCHY.md — пирамида приоритетов (чьё слово главнее при конфликте).
AGENT.md — маршрутизатор команд (что делать по /consult, /client и т.д.).
learning/corrections.md — накопленные исправления прошлых ошибок.

learning/new_knowledge.md — новые знания от пользователя.
Если в пользовательском сообщении нет команды из AGENT.md — отвечай как обычный ассистент, никаких пайплайнов не запускай.

Операционные правила для Cline
Git и коммиты
Не делать git push без явного «Approve» от пользователя. Commit локально — можно, push — только по разрешению.
Перед коммитом всегда показывать git --no-pager diff <файл> для проверки.
Сообщения коммитов — на русском, формат: тип(область): краткое описание. Типы: feat, fix, chore, docs, refactor.
Не использовать git commit --amend, git rebase, git reset --hard без явного разрешения.
Не трогать ветку main напрямую. Работаем в текущей рабочей ветке.
Работа с файлами
Никогда не редактировать эталоны (1expert_style_example.md.txt, 1client_style_example.md.txt).
При создании новой консультации сохранять в clients/[Фамилия]/[ДАТА]_consult_expert.md (формат даты: ГГГГ-ММ-ДД).
При сомнении в пути — спросить, не угадывать.
Не создавать новые папки в корне без обсуждения.
Имена клиентов
В clients/ есть папки и на латинице (Karaianova/), и на кириллице (Владимир/). Использовать существующее имя папки клиента как есть, не переименовывать. Если папки нет — спросить пользователя, как назвать.

Поведение в чате
Если задача неясна — задать ОДИН уточняющий вопрос, не пять.
Если файл не найден дословно как ожидалось — остановиться и доложить, не угадывать содержимое.
Не делать «творческих интерпретаций» инструкций пользователя. Что написано — то и делать.
Перед командами в терминале (особенно с rm, mv, git push) — показать команду и ждать подтверждения.
Терминал
Git установлен и работает в PowerShell. Использовать команды напрямую.
Для длинных diff использовать git --no-pager diff (без пейджера, чтобы не зависал).
GitHub CLI (gh) пока не установлен — PR закрываются через веб-интерфейс GitHub.
Что делать при конфликте инструкций
Если две инструкции из разных файлов противоречат друг другу:

Применить иерархию из v2/HIERARCHY.md (Уровень 1 → Уровень 7).
Сделать выбор в пользу верхнего уровня.
Записать конфликт в learning/corrections.md с пометкой, какой уровень победил и почему.
Не молчать о конфликте. Не пытаться «совместить» противоречивые правила.

Протокол закрытия сессии
ОБЯЗАТЕЛЬНЫЙ чек-лист в конце каждой рабочей сессии. Выполняется явно, с проговариванием каждого пункта в чате перед финальным коммитом. Источник правила: learning/corrections.md, запись от 2026-06-04 (Сессия 13).

1. Файл(ы) сессии созданы и запушены. Подтверждение — конкретный коммит-хеш из git log --oneline -5.
2. v2/SOURCES_INDEX.md обновлён — новые протоколы добавлены как Protocol ⭐, старые выжимки помечены DEPRECATED.
3. project/STATUS.md → блок «Последняя сессия» — заменён на текущую сессию (что сделано, какие коммиты, ключевые решения).
4. project/STATUS.md → таблица «История сессий» — добавлена НОВАЯ строка про закрываемую сессию (одна строка: дата, название, краткий результат, коммит). КРИТИЧНО: этот пункт системно пропускался в Сессиях 9–12, проверять обязательно.
5. project/STATUS.md → блок «Следующая сессия» — актуализирован под реальный следующий шаг (не оставлять устаревший план от прошлых сессий).
6. Финальный коммит вида docs(status): закрытие Сессии N — <тема> с push в рабочую ветку.

Если хотя бы один пункт не выполнен — сессия НЕ закрыта. Не объявлять о завершении работы, пока все 6 пунктов не отмечены.

Протокол верификации создания файлов
ОБЯЗАТЕЛЬНОЕ правило для всех команд, создающих/изменяющих файлы.

После выдачи команды Set-Content (или любой другой команды записи в файл) агент обязан:

1. Явно потребовать от пользователя вывод (Get-Content <путь> -Encoding UTF8).Count.
2. НЕ двигаться к следующему шагу workflow до получения числа строк.
3. Формулировка обязательная: «Жду число строк. Не закрываю задачу, пока не увижу вывод».

Принцип «команда выдана = задача выполнена» ЗАПРЕЩЁН. Команда выдана = ждём подтверждения от терминала.

Старт новой сессии — аудит хвостов
В начале каждой новой сессии (перед началом основной работы) выполнить:

Test-Path references\methodology\<последний_созданный_файл>.md
git log --oneline -5
Get-Content project\STATUS.md -Encoding UTF8 | Select-String "^\| 2026"

Если последний созданный файл из STATUS.md не существует, или его нет в логе коммитов, или последняя сессия из «Последней сессии» отсутствует в таблице истории — поднять флаг пользователю ДО начала новой работы.
